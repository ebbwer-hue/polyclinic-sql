# ПЗ 3.1. Поликлиника

Готовое решение для Microsoft SQL Server находится в файле polyclinic.sql.
Откройте файл в SQL Server Management Studio (SSMS), подключитесь к своему серверу и нажмите F5.
Скрипт предназначен для первого запуска: база Polyclinic_PZ31 ещё не должна существовать.
Все люди и записи в примере вымышлены.

## Таблицы и связи

| Таблица | Содержание |
|---|---|
| Specialties | Специальности врачей |
| Doctors | Врачи и номера их специальностей |
| Patients | Пациенты и даты рождения |
| Diagnoses | Справочник диагнозов |
| Appointments | Приёмы: пациент, врач, диагноз и дата со временем |

В каждой таблице ровно пять записей. В учебной модели у врача одна специальность, у приёма один диагноз.

Связи «один ко многим»:

- Specialties → Doctors: к одной специальности относится несколько врачей.
- Doctors → Appointments: один врач проводит несколько приёмов.
- Patients → Appointments: один пациент может приходить несколько раз.
- Diagnoses → Appointments: один диагноз может встречаться на разных приёмах.

Внешние ключи запрещают приём с несуществующим пациентом, врачом или диагнозом, а также врача с несуществующей специальностью. Они также не позволяют удалить используемую родительскую запись, пока на неё есть ссылки.

## Почему это третья нормальная форма (3НФ)

1. Первая нормальная форма: в каждой ячейке одно значение, списков специальностей или диагнозов в ячейке нет.
2. Вторая нормальная форма: первичный ключ каждой таблицы состоит из одного столбца. Неключевые поля зависят от всего ключа.
3. Третья нормальная форма: неключевые поля не зависят друг от друга. Например, название специальности хранится в Specialties, а не дублируется в Doctors. В Appointments хранятся номера пациента, врача и диагноза; их имена и названия берутся из связанных таблиц.

Полное имя хранится одним значением: для этой работы отдельная обработка фамилии, имени и отчества не требуется.

## Что показывают запросы

1. LEFT JOIN выводит всех пациентов и даты их приёмов. Пациент № 1 был дважды, поэтому отображается двумя строками. У пациента № 5 нет приёмов: он всё равно отображается, а дата равна NULL. Всего шесть строк.
2. RIGHT JOIN выводит всех врачей и даты приёмов. Врач № 1 отображается дважды. У врача № 5 приёмов нет: дата равна NULL. Всего шесть строк.
3. INNER JOIN объединяет все пять таблиц: показывает пять приёмов с именами пациентов, врачей, специальностями и диагнозами.
4. В учебном примере временно отключается только FK_Appointments_Patients. У приёма № 5 номер пациента меняется с 4 на 999. Так создаётся нарушение ссылочной целостности: приём ссылается на отсутствующую запись.
5. LEFT JOIN и RIGHT JOIN находят одно и то же нарушение: приём № 5 с PatientID = 999. Таблицы поменяны местами, чтобы оба запроса сохраняли все приёмы.
6. UPDATE возвращает заранее известный правильный PatientID = 4. Затем WITH CHECK CHECK CONSTRAINT проверяет данные и восстанавливает защиту. Число строк не меняется.
7. Последний запрос не выводит строк: ссылок на отсутствующих пациентов больше нет.

Пациент без приёмов — нормальная ситуация. Приём с несуществующим пациентом — нарушение ссылочной целостности. INNER JOIN скрывает такую ошибочную строку, поэтому для её поиска используются внешние соединения и IS NULL.

В настоящей базе нельзя угадывать, кому принадлежит ошибочный приём. Здесь PatientID = 4 известен из исходных учебных данных.

## Короткое объяснение для защиты

«Я создал базу “Поликлиника” из пяти таблиц в третьей нормальной форме и добавил по пять записей. Таблицы связаны первичными и внешними ключами. LEFT JOIN сохраняет все строки слева, RIGHT JOIN — справа. Я временно отключил внешний ключ и указал у одного приёма несуществующего пациента. Нашёл нарушение обоими соединениями, исправил номер пациента и снова включил внешний ключ с проверкой данных».
